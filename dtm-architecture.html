Before anything else — live exposure in the current web root

public_html/backup.php is reachable by anyone, with no login and no token. Requesting it runs db_dump.php (a full mysqldump) with a hardcoded plaintext DB user/password, then zip.php, which zips the entire site — wp-config.php included — and writes both the raw .sql and the .zip straight into the public web root, where they're downloadable by anyone who requests the resulting filename.

The DB name inside backup.php (srv48172_person-all_pl) doesn't match this site's own DB (srv48172_delegatetomate_pl) — it looks like a leftover from another project on the same hosting account. Stale or not, the script is live, unauthenticated, and writable output lands in a public directory.

Before the next step
  • Check the hosting file manager / access logs for any existing db_backup_*.sql or www_backup_*.zip in public_html and delete them now.
  • Delete or move backup.php, db_dump.php, zip.php out of the web root entirely — they're not part of WordPress.
  • Rotate the DB password they contain, on both databases in that hosting account.

01Current architecture

Everything below is inferred from the files on disk — no custom plugin, no custom PHP logic beyond the purchased theme. It's a page-builder site: content lives as Elementor JSON in the database, not in template code.

02What the page actually is

One landing page, nine sections, no blog in use, no user accounts, no e-commerce. The "app" is a marketing page plus a contact form.

03What the host actually allows

Since the app has to stay on this server, its runtime menu — not preference — sets the boundaries of the stack choice.

  • Confirmed: LiteSpeed, PHP 5.6–8.5, MySQL/MariaDB, cPanel, FTP — what's serving the site today.
  • Confirmed: seohost's cPanel includes an Application Manager for Node.js (and Python) apps via Phusion Passenger, plus SSH access — no manual reverse-proxy setup needed.
  • Not offered: no evidence of Go (or any arbitrary-binary) support in seohost's shared plans — Passenger's app manager covers Node and Python specifically. Go would need a VPS.

That rules out your Go guess for this server, unless the plan gets upgraded to a VPS later. React survives either way — the open question is whether it needs a live Node process behind it at all.

05Recommendation

Start static-first: React (via Astro, or plain Vite) built to static HTML/CSS/JS, pushed to public_html over FTP — no PHP, no WordPress, no DB in the request path for a page view. It matches the traffic, matches the FTP-only deploy habit already in place, and removes the entire plugin/DB attack surface that produced this session's security finding. Keep the contact form server-side via a single small PHP script (the one piece of backend logic that still earns its keep), or hand it to a third-party form endpoint if even that's unwanted.

Drop Go for this server — it's not in seohost's supported runtimes without a VPS upgrade, and nothing about a low-traffic marketing page needs it. If a future feature genuinely needs per-request server logic (a login area, live pricing, a booking flow), the Node.js path is already there in cPanel and doesn't require re-deciding the front end — Next.js can render the same React components dynamically.

Open before scoping the build

Does anyone who isn't touching code need to edit copy or pricing later? If yes, a static build needs either a lightweight headless CMS or a "content lives in the repo, edits go through a PR" workflow — worth deciding now, since it shapes the build.

Contact form destination

Keep PHP mail()/SMTP on this host, or route through a hosted form API? The latter drops PHP from the stack entirely, at the cost of a third-party dependency for lead capture.

Anything beyond this one page planned?

A blog, multi-language, or gated content would tilt the answer toward Next.js sooner rather than later — worth naming now if it's on the roadmap, even loosely.
